B. STRUCTURE OF SYSML V2: WHAT AN AI MUST KNOW
1. KerML supplies the foundational semantic concepts; SysML v2 is a systems-engineering language built on it. SysML v1 relies on a UML profile; SysML v2 is not a UML stereotype rename.
2. Definition versus usage is core: definitions define reusable type/design concepts; usages introduce features/instances in a model context. Distinguish part def vs part, port def vs port, item def vs item, action def vs action, state def vs state, requirement def vs requirement, and attributes/constraints/calculations as appropriate. Qualify reuse and typing; never infer semantics solely from the visual label.
3. Namespaces, packages, imports, memberships, features, typing, specialization, subsetting, redefinition, bindings, feature chaining, and expression evaluation are structural first-class concepts. An apparently simple owner/type change can create or move explicit relationships; do not manipulate v2 element relationships like plain scalar fields.
4. Structure and interaction: parts, ports, interfaces, connections, items, flows, conjugated ports; distinguish physical/logical decomposition from data/value transfers.
5. Behavior: actions, successions, accept/send actions, state definitions/usages and transitions. Validate ordering, guards and value types.
6. Requirements and analysis: requirement definitions/usages, satisfy and verification relationships, constraints, calculations, units, quantities, evaluation, and traceability. Static evaluation and dynamic simulation are different capabilities with separate prerequisites.
7. Visualization: textual, graphical and tabular views may be generated from query/expressions; a diagram SVG is a presentation, not a complete semantic interchange or edit representation. View definitions and viewpoint intent matter.
8. Model libraries: pin libraries and versions (Quantities and Units, Geometry, Analysis, Cause and Effect, Metadata, Requirement Derivation, Systems Library). Imports and units must resolve in the target tool before declaring a text file valid.
9. Parser posture: Any sample syntax generated by an AI must be checked by a target release's textual parser plus model validation before being labeled executable. Prefer official simple-vehicle examples and quick sheets; never guess complex language keywords or API signatures.

E. MODELING WORKFLOW / TEXT EDITOR SAFETY
Vendor describes separate textual editor Synchronize and project Save actions. Explicitly synchronize text edits before saving the project; unsynchronized text may not be included in saved model. Concurrent editing in the text editor and elsewhere may lead to overwrite when choosing Refresh or Synchronize. A validation/synchronization setting can alter handling of errors. The vendor's documentation sections appear inconsistent about default/true/false behavior, so inspect the actual installed 2026xR1 option and test invalid syntax on a disposable local model before enabling any permissive mode. Do not use a purported default to justify saving invalid models.
Official textual guide: https://docs.nomagic.com/SYSML2P/2026x-refresh1/managing-textual-editor-304004737.html
Recommended loop: freeze branch/commit baseline -> resolve namespace -> GET or open text -> snapshot + hash -> modify isolated local model -> synchronize -> validate references/types/memberships/units -> save -> compare semantic diff -> test branch commit -> read back via API and tool. Never use optimistic overwrite in production without preview and revision protection.
For cross-surface engineering automation, distinguish:
(A) Cameo desktop OpenAPI for v1 UML/profile editing;
(B) v2 desktop Open API technology preview;
(C) standard SysML v2 TWC REST/HTTP API;
(D) TWC vendor textual/graphical services;
(E) OSLC/DataHub external linking/synchronization.
No surface is an automatic substitute for another. Do not invent endpoint paths, Java methods, or authentication formats.
F. SYSML V1 -> V2 TRANSFORMATION / MIGRATION
The normative OMG language transformation specification is the standard semantic baseline, but migration support is vendor/product/release specific. On original 2026x documentation, use SysML v1-to-v2 Migration plugin, File > Export To > SysML v2 Model, which generates a separate local v2 project. Failure report name: MigrationReportOf<projectName>.xlsx with "Not Migrated Elements" and "Not Migrated Element Properties". The 2026x documentation warned partial metamodel coverage (~20%) and no diagram migration AT THAT VERSION. DO NOT extrapolate this numerical percentage or absence of diagram migration to Refresh1; 3DS explicitly says Refresh1 improves model/diagram coverage, but precise coverage must be measured in a test corpus.
Official: https://docs.nomagic.com/SYSML2P/2026x/migration-from-sysml-v1-to-sysml-v2-254423020.html
High-level mapping examples from 2026x docs (always inspect usage and semantics): Block->Part Definition; Interface Block->Interface Definition; Proxy Port->Port Usage; Part Property->Part Usage; Value Property->Attribute Usage; Constraint Property->Assert Constraint Usage; Requirement->Requirement Usage; Activity->Action Definition; State Machine->State Definition; Signal->Item Definition; Connector->Connection Usage or Interface Usage. No universal bijection; custom stereotypes, allocations, derived properties, diagrams, profiles, model history, report templates and external links require separate assessment.
Required migration manifest: input model ID + baseline commit/hash; tool and plugin exact versions; source element ID/type; target element ID/type; mapping rationale; cardinality and units; relationships preserved/changed; unknown/unmigrated reason; custom-profile treatments; orphan/external link inventory; diagram parity report; validation violations; reviewer and disposition; rollback reference.
Acceptance gate (test model first): 0 unexplained losses; no broken use/project libraries; compare package/type/instance/requirement counts; trace satisfy/verify relationships; check ports/interfaces/flows, value types/units, behavior/state transitions and constraints; verify regenerated textual parse; check tabular/graphic views; compare requirements IDs and external DOORS/Jama/ENOVIA references. "Migration completed" is not "functionally equivalent."

H. AI AGENT CAPABILITY CURRICULUM AND RECIPES
A base LLM claiming SysML v2 competence should be able to:
(1) explain KerML versus SysML v2, v1 versus v2, definitions/usages, namespaces, imports, feature typing, structural vs behavioral modeling;
(2) draft packages, definitions/usages, ports, interfaces/flows, requirements and analysis models in syntax pinned to a formal release;
(3) find parser errors and reconcile names/imports/units, ownership, multiplicities, specialization/redefinitions;
(4) generate and validate graphical/tabular/textual views from a model query;
(5) navigate models through the standard Systems Modeling API, identify project/version/branch/commit/element IDs, page query results and check auth;
(6) use vendor textual and graphical extensions only when present in Swagger;
(7) build a migration plan/report from real v1 exported constructs and retained identifiers;
(8) classify all transformation omissions and unintended semantics before any commit;
(9) distinguish static evaluation from dynamic simulation preview;
(10) produce testable requirements-to-design-to-verification traceability.
Example LAB A (language): represent a subsystem as a part definition, two part usages, port interfaces and a constrained attribute with unit; run parser/validation and document generated relationships.
LAB B (requirements): requirement def/usage -> satisfy -> verify evidence -> table; detect broken references.
LAB C (TWC API, read-only): obtain current project/branch/commit; GET elements and textual namespace; compare model count/name/type; GET a view SVG; document output hash. Disable mutation.
LAB D (migration): migrate a small 2024x v1 example into a SEPARATE 2026xR1 lab; compare reports, IDs, structure and diagrams; list all unsupported content.
LAB E (simulation): build a toy state/flow example in an isolated lab, note plugin technology preview and compare observed behavior with expected result.
LAB F (integration): import a non-sensitive synthetic requirement fixture using the licensed connector; check traceability and copy-data behavior.
AI output template: Target product/version/edition; model stack; execution API; license; source baseline; user authorization; read-only/mutating; exact installed Swagger/JavaDocs; parser/static validation/simulation test outcome; unresolved gaps. AI-authored examples are drafts until run.

LANGUAGE TOPIC -> KEYWORDS/STRUCTURAL QUESTIONS -> REQUIRED CHECK
1. Packages/namespaces/imports: package, import, public/private, alias, memberships -> namespace containment, visibility, name resolution, conflicting short names.
2. Identification/documentation: declared names/short names, doc/comment, reserved keywords, visibility -> stable element identity vs display name, comments vs executable constraints.
3. Typing/specialization: def, use, :, specializes (:>), subsets, redefines (:>>), ref, derived -> distinguish inheritance vs feature subsets/redefinition, inspect multiplicity.
4. Structure: part def/part, attribute def/attribute, item def/item, port def/port, interface def/interface, connection, bind -> usage context, ownership, ends, compatible types, value flow.
5. Interactions: in/out/inout, flow, send, accept, message -> roles, item type, source/destination, value transfer vs topology.
6. Behavior: action def/action, perform, first, then, succession, fork/join/merge, state def/state, transition, entry/do/exit -> sequencing, guards, events, active state and execution limits.
7. Requirements: requirement def/requirement, subject, assume constraint, require constraint, satisfy, verify, verification case -> source identifier, subject, validity of constraint, evidence and relationship target.
8. Calculation: constraint def/constraint, calc def/calc, assert constraint, expressions, units/quantities -> dimensional analysis, import/typing and Evaluation plugin limits.
9. Reuse/variability: libraries, specialization, variation/variant, allocation, dependency, occurrence -> semantic library rules, not v1 stereotype string substitutions.
10. Visualization: viewpoint, view, render, graphical/tabular/textual representations -> query scope, view definition, element ID, presentation not semantic export.
11. Metadata: metadata definitions/usages, annotations -> target and explicit relationship, not an arbitrary tag-like field.
12. Interoperability: projects/branches/commits/elements, queries and external relationships -> permissions, revision, indexing and returned schema.
ILLUSTRATIVE TEXTUAL TRAINING FIXTURE — VALIDATE WITH THE TARGET PARSER BEFORE RELYING ON IT:
package Example {
  part def Sensor;
  part def Controller {
    part primarySensor : Sensor;
  }
}
Part definition is a type; nested part is a usage, not a UML stereotype. Build richer fixtures for port/interface/flow, requirements and behavior only after resolving target imports/standard libraries. The official Annex A vehicle model demonstrates typed attributes, parts, ports, action/state definitions; use exact official syntax rather than an ellipsis as executable code.
Preserve stable requirement short IDs and external DOORS/DNG identifiers distinctly from model IDs/URIs.
